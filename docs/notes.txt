document processing pipeline for RAG
---------------------------------------

document loaders: extract text from raw files, handle different formats

text splitters: split into chunks of 500-1000 chars, preserve sentence boundaries, add overlap( 100-200 chars)
    context in text is important when splitting because we could split it in a weird way which if we give it to AI
    it may misinterpret it which is why we add overlap

    chunking is the MOST important part of RAG and can make or break it
    we must be strategic on how to chunk our documents

    four chunking variables that affect quality:
        1. chunk size (sweet spot: 200-1000 tokens)
        2. overlap (preserves context)
        3. split boundaries
            fixed, recursive (cut at paragraphs/sentences), semantic (cut at meaning), late (embed first, chunk later)
        4. content type (each needs specific treatment)

embedding generation: convert each chunk to a vector

vector storage

queries


recursive chunking:
    80% of product rag uses this
    split by "\n\n" = paragraphs
    split by "\n" = lines
    etc
    keep going down if the chunks are too big

Traditional Chunking vs Late Chunking:
    - traditional chunking loses cross-chunk context
    - late chunking is more accurate because the chunks know about each other

-----------------------------------------------------------------------------------
RAG PIPELINE:

phase 1: indexing
    load documents, chunking, embeddings, vector db

phase 2: querying
    embed question, search db, retrieve docs, llm, answer

must use same embedding model for embedding document and question

Hybrid search

vector searching sucks at codes, acronyms, and stuff like that. If you got a query like "SKV_1239123 Shoes",
it won't care bout the code cause it had no semantic meaning but will search stuff about shoes in general

bm25 search is good at finding codes, acronyms, etc but sucks at semantic meaning

hybrid search combines the two

pipeline:
query goes into both a vector search and a bm25 search
compares its found documents, ranking them, and them comparing their results through "reciprocal rank fusion" RRF score = 1(k + rank)
then we get the final results

documents good in both rise to the top

hybrid should be used when data has codes/ids, legal documents, mixed query types, and where accuracy is critical
